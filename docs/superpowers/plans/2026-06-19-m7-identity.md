# M7 — Identity / Reputation (E7, thin) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use the locked build loop (red → impl → green → full suite + typecheck + lint + build → mark plan checkbox → append log-server). Steps use checkbox (`- [ ]`) syntax.

**Goal:** Ship the read-side of Engine 7 (Identity / Reputation) — the "trust layer" — fully decoupled from custody and the payment hot path: ERC-8004 passport resolution (read-side), the anti-wash-trading reputation compute (BUG-28), a reputation read API that serves discovery, and a behavioural invariant proving a reputation outage can never block or alter a policy-valid payment.

**Architecture:** Reputation is READ-SIDE ONLY. ServiceScope is a static allowlist precompiled into `effective_policy`; the enforcement hot path has NO call into E7 (engine-specs-FINAL.md:241-243). On-chain registry reads/writes (ERC-8004 Identity / Reputation registries) sit behind injected seams (mirroring `TokenDomainSource` / `NonceReconciler` in `lib/arc/client.ts`), so the L1-L7 engines stay Testcontainers-only and the viem layer remains the sole creds-gated seam (wired in M9). The reputation score is computed from the cold ledger's settled-job facts (`spend_events`); the on-chain C-9 post is a placeholder seam (read-side is the Phase-1 value; on-chain verdict recording is deferred to the mainnet governance spec, BUG-35).

**Tech Stack:** Node 20 + TS strict (NodeNext ESM, `.js` imports, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`) · pg · ioredis · Vitest + Testcontainers (postgres:16-alpine, redis:7-alpine) · ESLint-9 flat (no-console, no-unsafe-member-access).

| E7 component | M7 thin cut | Citation |

| On-chain identity binding (ERC-8004 Identity Registry) | **L1** — read-side passport resolve behind a seam | engine-specs-FINAL.md:226, control/types.ts:35 |
| Reputation Registry + Verifier service (anti-wash-trading) | **L2 + L3** — compute (BUG-28) + read API; C-9 post placeholder seam | engine-specs-FINAL.md:227,229-230,233 |

| 7-dim agent rating / 6-dim endpoint rating | discovery-UI enrichment, deferred; the BUG-28 aggregate score IS the Reputation Registry's stored value | engine-specs-FINAL.md:229 (formula is the locked reputation definition) |

### Escrow deferral — cited rationale (NOT a silent cut)

SPIKE-01 (PHASE-1-SPIKES.md:17-23) explicitly states: *"Blocks: Build-order step 5 (Engine 7 Signature-as-Escrow feature). Run before: any escrow-dependent feature is scoped for implementation."* It must confirm the EIP-3009 `cancelAuthorization` nonce-consumption primitive on the deployed Arc Testnet contract **and** establish its gas cost.

The escrow feature cannot be safely *partially* built either, because F-4 (engine-specs-FINAL.md:230) makes **two-sided** gas-budget controls a hard requirement: *"because creating an escrow manufactures a future cancellation gas liability, both sides need budget controls."* The cancellation-side controls — F-4b (cancellation VelocityLimit) and F-4c (Escrow Gas-Budget Ceiling) — depend on SPIKE-01's cancellation primitive and its measured gas cost (the spec says verbatim: *"Gas-cost pricing depends on SPIKE-01's cancellation primitive"*). Building escrow-create without its mandated cancellation budget controls would violate F-4.

SPIKE-01 requires a live Arc Testnet transaction (creds-gated), out of this Testcontainers-only milestone. Therefore the entire Signature-as-Escrow subsystem is deferred until SPIKE-01 runs — honouring the spike's own gate. Escrow off-ramp is read-side for trust and never blocks an unrelated payment (engine-specs-FINAL.md:239), so deferring it does not affect the Phase-1 payment path. The keyspace already anticipates it (`keys.escrowReserved`, keyspace.ts:40-41) and the EIP-3009 nonce seam pattern exists (`NonceReconciler`), so the build is ready the moment SPIKE-01 clears.

## M7.L2 — Reputation compute (BUG-28 anti-wash-trading), pure

**Files:** Create `src/engines/identity/reputation.ts` (the `computeReputation` pure function), `test/identity/reputation-compute.test.ts`. Modify `src/contracts/index.ts` (add `JobFact`, `ReputationResult`).

`computeReputation(facts: JobFact[], params, now) → ReputationResult` implements the locked formula `score = f(unique_counterparties, capital_at_risk, completion_rate, dispute_rate, recency_weight)` and ALL six anti-wash-trading rules (engine-specs-FINAL.md:229). Pure — no DB, no Redis — so it is exhaustively unit-testable. The combining curve `f()` is NOT specified by the spec (only its inputs + rules are); its weights are **parameters**, not frozen constants — calibration is a follow-up (cite: spec gives factors + rules, not a closed form; same posture as SPIKE-02 watermark). Reputation is a dimensionless trust score, NOT money → `number` arithmetic is acceptable; `capitalAtRisk` stays `bigint`.

`JobFact` (C-8 settled-job fact, engine-specs-FINAL.md:58): `{ counterparty: string; counterpartyOrgId: OrgId | null; agentOrgId: OrgId; capitalAtRisk: UsdcBaseUnits; completed: boolean; disputed: boolean; settledAt: number }`.

Locked rules, each its own one-claim test:
- [x] **Step 1 (RED):** Six tests in `reputation-compute.test.ts`:
  1. **UNRATED gate** — fewer than 5 unique counterparties OR < $10 capital-at-risk OR < 7 days history → `{ rated: false, status: 'UNRATED' }` (rule 6).
  2. **Self-loop exclusion** — facts where `counterpartyOrgId === agentOrgId` are dropped before scoring (rule 1): an agent that only traded with its own org is UNRATED.
  3. **Dust + min-capital exclusion** — a fact with `capitalAtRisk < $0.10` or `< $1` is excluded (rule 3): dust-only history is UNRATED.
  4. **Cross-org collusion damping** — counterparty diversity is weighted so N facts spread across few distinct counterparties score strictly lower than the same N facts across many distinct counterparties (rule 2).
  5. **Recency decay** — an old settled fact (age ≈ one 90-day half-life) contributes ≈ half the recency weight of a fresh one (rule 4): same facts, older `settledAt` ⇒ strictly lower score.
  6. **Dispute penalty** — a disputed fact lowers the score proportionally vs the same fact undisputed (rule 5).
- [x] **Step 2:** Run, watch all six fail.
- [x] **Step 3 (GREEN):** Implement `computeReputation`: filter (self-loop, dust/min-capital), gate UNRATED on the three thresholds, then combine the five factors with parameterized weights (recency_weight `= 0.5 ** (ageDays / 90)`, diversity weight on `uniqueCounterparties`, dispute penalty proportional to disputed value). Tests assert RULE DIRECTION / monotonicity, never magic score values.
- [x] **Step 4:** Run, watch all six pass.
- [x] **Step 5:** Full suite + typecheck + lint + build.
- [x] **Step 6:** Mark checkbox group; append log-server.

**As-built (L2 DONE+green):** contracts/index.ts += `JobFact` (C-8) + `ReputationResult` (UNRATED | rated{score,uniqueCounterparties,capitalAtRisk:bigint}). `reputation.ts` `computeReputation(facts, {now, weights?}) → ReputationResult`, pure. Spec-locked thresholds as named constants (MIN_CAPITAL_PER_JOB $1, MIN_UNIQUE 5, MIN_TOTAL_CAPITAL $10, MIN_HISTORY 7d, RECENCY_HALF_LIFE 90d); the combining curve f() weights are `ReputationWeights` PARAMS (calibration, not frozen — spec gives factors+rules, not a closed form; SPIKE-02-style posture). Score is Number in [0,1] (trust, not money); capitalAtRisk summed/returned bigint. Rules: 1 self-loop drop (counterpartyOrgId===agentOrgId), 2 diversity-capped-at-target (volume can't farm), 3 sub-$1 jobs excluded (subsumes dust), 4 capital-weighted mean recency 0.5^(ageDays/90), 5 dispute penalty ∝ disputed-value fraction, 6 UNRATED gate. `reputation-compute.test.ts` 7/7 (rated baseline + 6 rule-direction tests; a test typo — `.rated` vs full object — was fixed, not an impl change). ## M7 adversarial review (Challenge Protocol)

- [x] Independent reviewer (general-purpose, no rubber-stamp) over passport.ts, reputation.ts, contracts, and the three test files + the ledger source. 11 findings; Challenge Protocol applied to each. **4 FIXED, 1 deviation-claim REJECTED-after-spec-reread, rest PASS-with-acknowledgment.**

**FIXED (REVISE):**
- **#2 (MED) history-span bug** — `oldest` was seeded with `now` in the reduce, so a `now` predating all settled jobs (clock skew / stale `now`) collapsed `historySeconds` to 0 and wrongly forced UNRATED, erasing a real history. Fix: seed the min with `Infinity` (counted is non-empty) and clamp `historySeconds = max(0, now − oldest)`.
- **#8 (HIGH) weak decouple invariant** — the behavioural test (UNRATED agent still ALLOWed) is necessary but not sufficient; a coupling that denied a *different* case would slip past. Fix: added a STRUCTURAL guard — scan the authorize-spine engines (enforcement/oracle/resolution) and assert NONE imports the reputation module (it stays `identity`-aware for domain-binding, but `reputation` must not appear). Made it cwd-independent (resolved via `import.meta.url`) with anti-vacuous guards (dirs must exist, files must be scanned) after catching that a drifted `process.cwd()` could have made it pass vacuously.
- **#7 (MED) zeroable diversity** — rule-direction-only tests would pass even if the anti-wash diversity weight were driven to ε. Fix: the cross-org damping test now asserts the score gap is MATERIAL (`> 0.05`) under the shipped default weights, so rule 2 cannot be silently neutralized.
- **#11 (LOW) shared UNRATED singleton** — returned from multiple exits, unfrozen. Fix: `Object.freeze(... as const)`.

**REJECTED (deviation claim) — #5 (HIGH) rule 3 "no-fork":** reviewer argued the per-job ≥$1 filter drops $0.10–$1 jobs the dust rule would keep. Re-read engine-specs-FINAL.md:229 verbatim — *"dust < $0.10 excluded, min $1 capital-at-risk to count"*: `$1` is grammatically the "to count" floor and an aggregate-$1 reading is dead (rule 6 already gates ≥$10 aggregate). So per-job ≥$1 is the literal, dominant read; the reviewer's ≥$0.10 alternative would drop the "min $1 to count" clause. Behaviour unchanged; the comment was corrected to cite both thresholds and explain why $1 binds (the reviewer's valid secondary nit).
